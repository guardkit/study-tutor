## 1. Where gamification is now (verified 2026-07-12)

- The **design is complete and fixed**: `docs/gamification/design.md` (Phase 0, reconciled to Postgres 2026-07-03) specifies the full economy — XP 60/120/180 + bonuses + ×1.25, 3-of-8 daily challenges, weekly quests, Boss Battles at L8, 15 levels 0→18,500, ~40 achievements in 6 categories, confidence bands 40/60/80, Reachy "Scholar" narration, a 9-element dashboard. Design principle: solo-learner, personal growth not competition.
- The **state engine was never built** (FEAT-PH2-001 = FEAT-PO-007; ADR-ARCH-013 still Proposed). The Graphiti-era plans (`phase-2-scope.md`, `phase-2-build-plan.md`) are **stale** — retired persistence model, do not build from them.
- What shipped (`90f1ed4`, 2026-07-09, via FEAT-VOICE-004 R05): `src/study_tutor/gamification.py`, a read-time projection (XP derived from `last_activity − started_at` of ended sessions, 15 level tiers verbatim, UTC-day streaks) behind `GET /api/student-model`; `near_achievements` hardwired `[]`. `session.xp_awarded` is write-only-always-0; the `achievement`/`quest` tables and Pydantic entities are fully dangling; planner stubs (`planner/pipeline.py:219,225`) await the engine.
- The **event system is hollow**: only `session.completed` is emitted (MCP only, payload violates `events-schema.yaml`, `subject_slug` actually carries the student id), to a bus with zero subscribers; the HTTP/WS/voice surface has no event infrastructure at all.
- The **Flutter app** has zero gamification surface and zero theming (explicit v1 scope), plus real defects: production `VoiceRecorder.stop()` uploads a 100-byte placeholder (real mic audio never uploaded), TTS never played (`just_audio` declared, unused), WS streaming adapter built but never wired, frozen recording timer, 15–30 s frozen UI on send.

### 1.1 The W0 bug — live session-ends silently drop learner state (fix first)

`SessionService.end_session` (`session/service.py:406-416`) calls `store.end_session` — which flips `status='ended'` in its **own** transaction — *before* `store.record_session_completion`, whose idempotency gate is `ON CONFLICT … WHERE status != 'ended'` (`postgres.py:780-794`). The gate therefore never fires: `transition_happened` is always False and **all completion children — confidence updates, misconceptions, xp_awarded, topic, aos_scaffolded — are silently skipped on every live MCP session-end since the SMP cutover.** Two independent verification agents found this. Why tests pass: the fake store gates idempotency on a separate `_completed_sessions` set (`fakes.py:222-224`) and its `end_session` doesn't participate; integration tests call `record_session_completion` directly, never the composed service path. Damage bounded by the 2026-07-09 NAS wipe (days of data, one student). **Fix:** land a *failing* composed-path integration test (service-level end-with-completion against real Postgres asserting confidence rows land), then the minimal ordering fix. This commit is independent of, and precedes, everything below.

### 1.2 The adaptive loop is severed end-to-end (fix after W0, before the engine — ratified)

Design intent (design.md §6.2/§6.3, container.md): Coach grades the session → confidence delta lands → planner reads the distribution → next topic chosen adaptively → topic shapes the material presented. A four-agent review (run `wf_f41e9839-be8`, 2026-07-12) verified **every link is broken**:

1. **Write severed** — the §1.1 bug drops completion children on MCP ends; HTTP ends pass `completion=None`; and even absent the bug, **no code ever creates a `topic_confidence` row** (`completion.py:140` is update-only) — the table is empty in production.
2. **Planner starved, and MCP-only** — rules 3/4/6 (the confidence consumers) rank over the empty table and never fire; every real session resolves to Rule-1 learner override or the baseline: the *first entry of `curriculum_defaults.yaml`* ("metaphor identification"), forever. `plan_session` has exactly one caller — the MCP adapter (`adapter.py:268`); the HTTP/Flutter path never plans at all. The adapter also passes no `ao_mapping`/`session_completions` (so rule-selected plans ship `focus_aos=[]` and every misconception counts "unrevisited"), plans live only in an in-memory dict (adapter restart loses them mid-session), and planner reads key by the subject slug while confidence writes key by ownership identity.
3. **The plan never reaches the material** — the Player (the model generating everything the student sees) deliberately ignores `SessionState` (`llm_player_adapter.py:149-159`, an explicitly reserved seam): its prompt is the static persona + the latest learner message, nothing else. The plan topic reaches only the Coach's *grading* prompt — and the production Coach is async and logger-only (ADR-ARCH-026 D1), so it cannot alter presented material either.
4. **No in-session memory on any transport** — `LLMClient.generate` sends `[system, latest user message]` only (`llm/client.py:178-185`); durable transcripts are never rehydrated. Every turn is stateless at the LLM level: the tutor cannot reference what the student said one turn ago.
5. **No difficulty adaptation exists** — GOAL.md §7's grade-target calibration is prompt-level and was never wired; no doc links stored confidence to difficulty (confidence was only ever designed to pick *which* topic). Grade 8–9 stretch exists solely as an XP-multiplier concept.

Also surfaced (needs runtime confirmation on the GB10 deployment): the REST voice-turn route is wired to a **placeholder echo** ("I understand your question: …", `voice/service.py:343-349`, wired at `cli/main.py:948-953`) rather than the orchestrator, and the WS streaming route passes a non-streaming `ReplyFn` where an async-iterator `ReplyStreamFn` is expected (`ws.py:190-192` vs `service.py:348`) — statically, every production WS turn would emit `generation_failed`. Combined with the app-side 100-byte recording placeholder (§5), the live voice path appears hollow at both ends.

For the record: the planner itself is **per-spec** (FEAT-PH1-002 shipped rules 1/3/4/6 with 2/5 as Phase-2 stubs) and demonstrably worked once — validation gate G3 flipped to Held on the 2026-05-07 Graphiti-era live demo. The starvation and the ordering bug were never recorded decisions; they are defects introduced/exposed around the SMP cutover. Separately, the planner as specified is narrower than design.md §6.3's promise (48 h cooldown vs 3-day spacing; no Struggling-first priority; the 4-day anti-repetition rotation was never carried over) — reconciled by ruling R11.

## 2. Settled decisions (this plan)

- **D1 — Engine = pure decision function + one finalize transaction, not an event subscriber.** `src/study_tutor/gamification/engine.py`: `decide(prior_facts, session_facts, now) → GamificationDecision {xp_awarded, total_xp_after, level_before/after, streak_days, streak_extended, unlocked[]}` — no I/O, injected clock. A new store method `finalize_session(...)` replaces the broken two-call sequence: single transaction whose first statement is `UPDATE session SET status='ended', … WHERE session_id=:sid AND status='active' RETURNING …` — that gate **is** the idempotency mechanism *and* returns the session facts. Then read prior facts in-txn, call `decide()`, write `session.xp_awarded` + `settled_at`, insert achievement rows (`ON CONFLICT DO NOTHING`), run the existing confidence/misconception helpers. Double-end / two-device races serialize on the session row lock; the loser replays the banked decision (via `achievement.session_id` + banked xp) so both devices see identical results.
- **D2 — Bank facts, derive aggregates** (honors `schema_reference.sql` ASSUM-002; reverses nothing). No `gamification_state` table, no running totals: `total_xp = SUM(session.xp_awarded) + SUM(achievement.xp_awarded)`; level, streaks, `near_achievements` derived at read time. W1 migration adds only: `session.settled_at` (nullable TIMESTAMPTZ — the sweep's work queue), `achievement.session_id` (replay), `topic_confidence_history` (append-only; **cannot be backfilled**, so capture starts day one even though Growth achievements come later).
- **D3 — Failure semantics: settlement can never block ending a session.** Settlement runs in a savepoint (`begin_nested()`); on fault, roll back to the savepoint, commit the end + completion, leave `settled_at` NULL, log loudly. A `study-tutor settle-sessions` CLI sweep (modeled on `seed-students`) settles anything ended-with-`settled_at`-NULL — it is load-bearing (fault recovery **and** historical backfill), not a convenience.
- **D4 — Single hook point = `SessionService.end_session`, both transports.** `build_session_completion` moves from the MCP adapter into the service; the HTTP handler's `completion=None` bypass (`http/app.py:369`) is deleted. This absorbs and closes TASK-APP1-04.
- **D5 — Engagement-time XP.** Duration = `max(ts) − min(ts)` over `session_turn` (server-stamped TIMESTAMPTZ on all transports incl. voice — verified), never `last_activity`, which is re-stamped at end-call and rewards idle time. Zero-turn sessions settle at 0 XP with `settled_at` stamped (sweep must terminate). Sessions under 2 min engagement bank 0 XP, including a legitimate single Q&A pair — ratified rule. Band cutoffs (<15 min → 60, <25 min → 120, else 180) ratified into design.md per §13 (they were implementation-invented).
- **D6 — Europe/London calendar, uniformly.** Streak credit day = London-local date of the session's **last turn**; the same ruling applies to Morning Star/Evening Scholar's 09:00/19:00 cutoffs and all week windows. Backfill uses identical rules.
- **D7 — Achievement XP cascades to a fixed point**, deterministic order streak → XP milestones → level milestones, so e.g. First Century carrying 100→150 XP resolves identically live and in backfill.
- **D8 — ADR-ARCH-013 is rejected/superseded** (new ADR): zero subscribers exist, the one emitter violates the schema, HTTP/voice have no bus, and asynchrony would violate design.md §11.2. The bus stays **notification-only, never state-bearing**; while there are still zero subscribers, flip the emit to after-commit with a schema-conforming payload (and fix `subject_slug`).
- **D9 — Contracts, two different weights.** Enriched `GET /api/student-model` (add `total_xp`, `level_number`, `xp_to_next_level`, `longest_streak`, `recent_achievements`, `near_achievements` as objects) = **additive §2.2 addendum**, no SHA re-pin; verified safe for Reachy (fleet-gateway passes the dict opaquely, gates only on `data_available`). Gamification block on `POST /api/sessions/{id}/end` = the **first-ever shape change to an original verb** → formal contract **Revision 2 via /design-refine**, re-pinned CONTRACT_SHA + new BINDING_SHA, block nullable so pinned clients and the hermetic fake stay valid; the MCP transport contract gets its own addendum.
- **D10 — Build now against table-token auth.** Keycloak A1–A3 are planned-not-started and KC-D6 guarantees the binding doesn't change at cutover. Obligations: the new Flutter port takes the `IdentityProvider` interface (KC-D7-proof), and the lane is **strictly student-facing** — no parent endpoints (KC-D5 reserves the parent role; that track's product design is its own future lane).
- **D11 — The static-HTML dashboard (FEAT-PH2-002 / design.md §10) is superseded by in-app Flutter surfaces.** It predates the app's existence. Reachy narration (§9) is unaffected — it reads the same enriched endpoint.
- **D12 — Two venue-pinned lanes** (Rich, 2026-07-12): Lane B (backend) on the GB10, Lane A (app) on the MacBook Pro. See §7.
- **D13 — Adaptive-loop repair is Lane B's first build stage (B0), after W0 and before the engine** (Rich, 2026-07-12). Scope in §7. Rationale: the engine's Mastery/Growth tranches, design §6.3's recommendations, and the whole "the tutor knows you" premise all read the same confidence data — repairing the loop first means the gamification engine lands on live signal instead of an empty table, and the student feels the product get smarter before it gets gamified. Confidence→difficulty linkage stays out of scope (no design connects them; future design work if wanted — GOAL.md §7 grade-target calibration is the difficulty mechanism and gets wired as prompt context in B0).
- **D14 — Transport-neutral core; MCP demoted to a thin optional adapter** (Rich, 2026-07-12: "we shouldn't be building MCPs into our core workflows — they are super inefficient"). Everything load-bearing moves into `SessionService`/store: planning happens inside `SessionService.start_session` (all transports, plan persisted on the session row — the adapter's in-memory `_plan_sessions` cache is deleted), completion assembly inside `end_session`, settlement inside `finalize_session`, events emitted by the service after commit. The MCP adapter keeps only tool-shape translation and remains useful as a Claude-Desktop dev/ops console; it may never again hold logic the HTTP path lacks. HTTP (+WS/voice) is the primary product transport — it is what the Flutter app and Reachy use.

**Explicitly NOT built this lane:** daily challenges, weekly quests, Boss Battles, streak freeze (design says Phase 2.5+), the §2.1 XP bonuses and ×1.25 multiplier (no per-turn signals yet), the event-subscriber engine, parent-facing surfaces, leaderboards (anti-goal by design), WebSocket push of gamification events, Reachy celebration scripting beyond what the enriched endpoint feeds.

## 4. Signal capture (W2 — small, each item unlocks named catalog entries)

1. **Confidence bootstrap** — *pulled forward into B0 (D13)*: today `topic_confidence` is empty forever in production: `build_session_completion` only updates pre-existing rows (`completion.py:140`) and nothing creates one. Create-on-first-study at a defined baseline (R12). Also un-starves design §6.3's adaptive recommendations.
2. **Canonical `text_name` on the session row at START**, from the corpus slug taxonomy (`macbeth`, `inspector-calls`, …) plus a genre/era mapping — replacing the MCP adapter's in-memory plan cache whose restart fallback writes the *student id* as topic (`adapter.py:461`). Topics as stored are free phrases ("dramatic irony in Macbeth"); text-level achievements are impossible without this.
3. **`quotes_embedded` per-session count** fed by the existing `quote_verifier` — highest signal-per-effort in the catalog (unlocks the +30 bonus, Quote Champion/Master, and daily challenge 2 later).
4. **Per-turn AO plumbing** — `session_turn.ao_scaffolded` exists in schema; the four `append_turn` call sites just never pass it.

## 5. App surfaces + UX revamp (Lane A)

Three product moments: **(1) Home header card** — level title + progress bar, streak flame, this week's XP, via a new `StudentModelApi` port/fake/http triplet on the established pattern; **(2) Session-end celebration sheet** — driven by the enriched end response (XP count-up, streak tick, unlock cards, level-up), zero extra latency and transactionally truthful — the single highest-value engagement moment in the design; **(3) Progress screen** — mastery grid (band colors as semantic theme tokens), achievement categories with near-miss progress, weekly XP.

**Phase A (attended Fable design pass, per the playbook's rule for non-crisp axes)** produces the design system + screen specs before any build wave: Material 3 `ColorScheme.fromSeed`, light **and** dark, "warm academic" register (§8 R2), typography with a scholarly display face, motion spec for celebrations, component specs. The UX-debt fixes ride the same lane: optimistic send + typing indicator (today: up to 15–30 s frozen UI), dismissible banners over blocking dialogs, timestamps, identity display + sign-out, animated scroll, subject title casing. **Voice defects fold in too**: real recording bytes (the 100-byte placeholder means live voice uploads garbage — relevant to FEAT-VOICE-004's smoke), TTS playback via `just_audio`, ticking record timer, relocate `VoiceRecorder` out of `lib/fakes/`.

## 8. Open rulings

- **R1 — "Macbeth Master" granularity (the one migration-shaping ruling).** The design awards mastery achievements at "80% confidence on the text", but the store keys confidence by *topic phrase* ("dramatic irony in Macbeth", "Lady Macbeth's ambition") — there is no "Macbeth" number to check. Options: **(a) aggregate** — text confidence = mean over that text's studied topics, gated on ≥3 distinct topics studied (recommended: no new schema beyond the W2 topic→text mapping; "mastered the text" means breadth, and the gate stops one strong topic awarding it); (b) strict aggregate — min over topics (harsh: one weak topic blocks forever); (c) a separate text-level confidence row the Coach maintains (second update path, more schema, more drift risk). **Recommendation: (a).**
- **R2 — design register.** The visual/tonal style Phase A designs to — including how loud the celebrations are. Recommendation: the "warm academic" brief already in the Phase-2 scope ("Obsidian meets Duolingo but GCSE-appropriate — engaging, not childish"): deep-ink/indigo base, warm gold accent, scholarly serif display headings, dark mode first-class; celebrations satisfying but brief (XP count-up, unlock cards, confetti only where design.md itself specifies it). Low-risk ruling: Phase A produces mockups Rich reviews before any build wave commits to them.
- **R3–R10 — spec-level wording rulings** (recommendations inline, to be ratified in the Phase A design.md patch): **R3** Morning Star/Evening Scholar = session *started* before 09:00 / after 19:00 London time, abandoned sessions don't count. **R4** First Steps requires a *completed* (≥2 min engagement) session — resolves the §2.1/§5.1 tension. **R5** No Weak Spots requires ≥5 studied topics. **R6** Climbing/Breakthrough = percentage-*points* over a rolling 7-day window (25 points needs ≥3 sessions under the ±10 cap — intentionally slow). **R7** Genre Gatherer week = Mon–Sun London calendar week. **R8** Quote Champion arbiter = `quote_verifier` corpus hits (deterministic), not Coach judgment. **R9** Six-AO Sampler = Coach-*observed* per-turn AOs (needs §4.4; stays W2+). **R10** Poetry Progenitor needs a Power & Conflict manifest (15 topics) — content task, rides W2.
- **R11 — planner spacing vs design.md §6.3** (B0): the shipped planner uses a 48 h cooldown with no Struggling-first priority and no rotation; the design promises Struggling-first, 3-day spacing, never-same-topic-4-days. Recommendation: design.md wins now that data will exist — implement §6.3 verbatim and retire the ASSUM-001 48 h interim.
- **R12 — baseline confidence for first-seen topics** (B0): recommendation 50 (mid-Developing) — a new topic is neither flagged Struggling nor near Mastered, and the first real Coach delta moves it honestly.
- **R13 — transcript window in the Player prompt** (B0): recommendation last 12 turns, token-capped, oldest dropped first; the durable store already holds the full transcript for resume.
